# Phase B — The Menu Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the game a front end — a title, a level select reading the manifest, a pause overlay and a results screen — plus the time controls (fast-forward, slow-motion) that the same machinery provides for free.

**Architecture:** Menus draw with the game's own quads on the 640×360 grid; no UI package. Every screen has a plain C# model holding its state and transitions, tested without a scene, and a thin MonoBehaviour that only draws it. Time control lives in the driver and the simulation cannot observe it: fast-forward runs *more fixed steps per render frame*, never a longer `dt`.

**Tech Stack:** Unity 6000.2.6f2, C#, IMGUI-free runtime rendering via the existing `QuadView`, NUnit EditMode tests. No new packages.

**Spec:** `docs/superpowers/specs/2026-08-24-menus-and-level-list-design.md` (sections 3 and 4; section 1 is built, section 2 is phase C)

## Global Constraints

From `CLAUDE.md` and the spec. Every task's requirements implicitly include these.

- **Determinism (GDD §6.1) is non-negotiable.** All simulation runs in `FixedUpdate` at 60 Hz. No `Time.deltaTime`, no `Random`, no wall-clock time in simulation code. Iterating an unordered collection where order affects the result is a defect.
- **`SimClock.Dt` is a compile-time constant and must not change.** Fast-forward is implemented as more `Tick()` calls per render frame, never as a larger `dt` and never via `Time.timeScale`. **The simulation must not be able to observe that fast-forward happened.**
- **Input is abstracted (GDD §5.5, LOCKED).** `IInputSource` emits intents, never raw keys, and downstream code must never learn the device. Adding a member to it is a LOCKED change requiring a dated row in `docs/balloon-game-gdd.md` §22 **in the same commit**.
- **Do not create or edit `.unity`, `.prefab` or `.asset` files.** Everything is constructed in code from the bootstrap.
- **Do not modify anything in `ProjectSettings/` without asking first.**
- **No `using UnityEditor;` outside test assemblies**, and never anywhere under `Assets/_Project/Scripts/LevelEditor/`.
- **Simulation logic stays in plain C# classes with no scene dependency**, and so does screen logic — that is what makes it testable.
- **Rendering:** 640 × 360, integer scaling only, 20 px tiles, point filtering. **Do not pixel-snap moving entities**; menu text and UI *may* snap to whole pixels, and should.
- **Reserved keys.** Gameplay uses `Space W A D J R Esc`, the arrows, and **left Shift** (bound to the context verb in `KeyboardInput`, alongside `J`). The editor uses `1 2 3 5 P U G H T L Delete` and `Ctrl+S/Z/Y`. New bindings must avoid all of these.
- **Run `./test.sh` before reporting any task complete.** Exit code 0 means every test passed. If it cannot run, say so explicitly and say why.
- **The Unity Editor must be closed** for `./test.sh` — batch mode takes an exclusive lock on `Library/`. If a run hangs beyond about two minutes, stop and ask for the editor to be closed. Never retry in a loop, never delete `Library/`.
- **Single-test runs:** `./test.sh -testFilter "KeepyUppy.SimTests.ClassName"`.
- **Unity `.meta` files** are generated by Unity's next run, which includes a batch-mode test run. Run the tests before `git add`, then commit the generated `.meta` alongside each new `.cs`.

```csharp
using UnityEngine;

namespace KeepyUppy.Sim
{
    /// <summary>
    /// How many fixed steps a render frame is allowed to run.
    ///
    /// **The simulation must never be able to observe this.** GDD 6.1 fixes the timestep at
    /// a compile-time constant, so speed is expressed as the NUMBER of 60 Hz steps taken per
    /// render frame — never a longer dt and never Time.timeScale. The same steps happen in
    /// the same order, so a fast-forwarded run is bit-identical to a normal one and the
    /// replay test cannot tell them apart.
    ///
    /// What changes is only how long a human waits. Every in-game clock — hazard periods,
    /// cooldowns, the balloon's descent — scales together, so GDD 4.3's "gravity is the
    /// clock" pressure is untouched. The player's own reaction time is the one real cost,
    /// which is why fast-forward is held rather than toggled.
    ///
    /// Slow motion is the same mechanism inverted, and is GDD 16's accessibility assist.
    /// </summary>
    public sealed class TimeControl
    {
        /// <summary>A guard on the tuning slider, not a design limit. See StepsFor.</summary>
        public const int MaxFactor = 4;

        /// <summary>Steps per frame while fast-forwarding. 1 is normal speed.</summary>
        public int Factor = 1;

        /// <summary>GDD 16: the 0.5x assist. Takes precedence over <see cref="Factor"/>.</summary>
        public bool SlowMotion;

        /// <summary>
        /// Steps to run on this render frame.
        ///
        /// A pure function of the frame number: slow motion drops every other frame by
        /// parity rather than by an accumulator, so there is no state to drift and none to
        /// reset when the room restarts.
        /// </summary>
        public int StepsFor(int renderFrame)
        {
            // An accessibility setting must not be overridden by a convenience one.
            if (SlowMotion) return renderFrame % 2 == 0 ? 1 : 0;

            return Mathf.Clamp(Factor, 1, MaxFactor);
        }
    }
}
```

```csharp
using UnityEngine;

namespace KeepyUppy.InputLayer
{
    /// <summary>
    /// Menu navigation intents.
    ///
    /// Separate from IInputSource on purpose: GDD 5.5's rule is that simulation code must
    /// never learn which device produced an intent, and menus are not simulation. Growing
    /// that interface for menu concerns would widen the surface ApplyHit sits behind for a
    /// reason unrelated to it.
    ///
    /// Navigation is one step per press, never per frame held: a repeating cursor races
    /// across a level grid faster than anyone can read it.
    /// </summary>
    public interface IMenuInput
    {
        /// <summary>One step, or zero. Up is +y, matching world space rather than screen space.</summary>
        Vector2Int Navigate { get; }

        bool Confirm { get; }
        bool Back { get; }

        /// <summary>Latch edges once per render frame.</summary>
        void Latch();

        /// <summary>Commit the latched edges. Called once, when the screen reads them.</summary>
        void Sample();
    }

    /// <summary>Replays scripted menu input. For tests; not a stub.</summary>
    public sealed class ScriptedMenuInput : IMenuInput
    {
        Vector2Int _navigate;
        bool _confirm;
        bool _back;

        public Vector2Int Navigate { get; private set; }
        public bool Confirm { get; private set; }
        public bool Back { get; private set; }

        public void Press(Vector2Int navigate, bool confirm, bool back)
        {
            _navigate = navigate;
            _confirm = confirm;
            _back = back;
        }

        public void Latch() { }

        public void Sample()
        {
            Navigate = _navigate;
            Confirm = _confirm;
            Back = _back;

            // Consumed: one press moves the cursor once.
            _navigate = Vector2Int.zero;
            _confirm = false;
            _back = false;
        }
    }
}
```

Latch edges in `Latch()` and commit them in `Sample()`, exactly as `KeyboardInput` does — read that file and mirror its structure, including its `Suppressed` handling if a dev panel owns the keyboard.

## Task 6: The bitmap font

**Files:**
- Create: `Assets/_Project/Scripts/Runtime/BitmapFont.cs`
- Test: `Assets/_Project/Tests/EditMode/BitmapFontTests.cs`

**Interfaces:**
- Consumes: nothing
- Produces: `KeepyUppy.Runtime.BitmapFont` — `const int GlyphWidth = 5`, `const int GlyphHeight = 7`, `const int Advance = 6`, `static bool Has(char c)`, `static ulong Rows(char c)` returning the packed bitmap, `static int Width(string text)`, `static Texture2D Atlas()` (built once, cached).

**This task contains authored data.** The plan specifies the encoding, the API and the tests; the glyph bitmaps themselves are drawn by the implementer. That is content, not a placeholder — but it means this task's review should check the *format* and the *API*, and check a couple of glyphs by eye, rather than verifying 40 bitmaps.

**Encoding:** one glyph is 7 rows of 5 bits, packed into a `ulong`, row 0 at the top, bit 4 at the left. So `A` — a filled triangle with a bar — is rows `01110 10001 10001 11111 10001 10001 10001`.

**Character set:** `A`–`Z`, `0`–`9`, space, and `. , : ! ? - / ' ( ) [ ] * + %`. Lowercase maps to uppercase — this is a 640×360 game and a 5×7 lowercase set with descenders is not worth it yet. An unknown character renders as a filled box so a missing glyph is visible rather than invisible.
